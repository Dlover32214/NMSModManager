# 提交约定

这篇不是凭空发明的格式，是从 `git log` 里归纳出来的。规范自 `a40b38a` 起成型，之前的提交是自由式中文短句。

---

## 1. 标题格式

```
type(scope): 中文一句话，说清改了什么
```

| 规则 | 说明 |
|---|---|
| 语言 | 冒号后用**中文** |
| 长度 | 一行，不折行 |
| 句号 | 不加 |
| 引号 | 用直角引号「」而不是 `"` |
| 语气 | 写「改了什么」，不写「update xxx」 |

真实标题：

```
fix(profile): 切换配置后补查模组健康信息
feat(ui): 全选改成可切换：全选之后就变「取消全选」
fix(drag): 插入提示线在行间空隙闪、拖到顶部消失
build: 构建脚本改用 pwsh 7，产物落 release\publish
```

`build:` 那次没带 scope，其余都带。

---

## 2. `type` 集合

| type | 用于 | 历史出现 |
|---|---|---|
| `feat` | 新功能 | ✅ 多次 |
| `fix` | 修 bug | ✅ 多次 |
| `style` | 纯外观调整，不改逻辑 | ✅ `style(ui): 去掉侧栏 logo 底板` |
| `build` | 构建脚本、工程配置 | ✅ `build: 构建脚本改用 pwsh 7` |
| `refactor` | 只改结构，不改行为 | ✅ 自 Core 拆分子目录起引入 |
| `docs` | 纯文档 | 预留，尚无历史用例 |

**不要用** `chore` / `perf` / `test`——历史里没出现过，本项目也没有测试项目。

区分要点：

- 改了行为 → `feat` 或 `fix`
- 只改结构/目录/命名空间 → `refactor`
- 只改构建流程 → `build`
- 只改文档 → `docs`

---

## 3. `scope` 集合

**scope 是功能域，不是目录名。** `ui` 覆盖 `ViewModels/` + `Views/` + `Themes/` 三处。

| scope | 覆盖范围 |
|---|---|
| `ui` | 界面与交互（含侧栏、Toast、状态栏） |
| `profile` | 配置（多套启停组合、切换、幽灵条目） |
| `drag` | 拖拽排序与拖放导入 |
| `library` | 模组库、外部模组收编 |
| `log` | 日志与诊断 |
| `amumss` | AMUMSS 检测/分析/重建/收集 |
| `safety` | 路径安全、库损坏守卫 |
| `app` | 应用生命周期（单实例、启动、崩溃） |
| `build` | 构建脚本 |
| `ci` | GitHub Actions |
| `core` | Core 项目结构与命名空间 |

新功能域出现时直接新增一个小写英文词，不需要提前申请。

---

## 4. 正文结构

有正文的提交占多数（最近 40 条里 25 条带 body）。模板固定为三段：

```
type(scope): 中文标题

为什么改 / 原来的问题（1–2 句，常带具体现象，讲问题不讲改动）

- 改动点一：具体做了什么，必要时带参数或常量（MaxWidth 180 → 300）
- 改动点二：……
- 改动点三：……

验证：<怎么证明改对了>
```

关键点：

1. **第二段讲「为什么」，不是「改了什么」**。改动细节留给列表。
2. **列表用 `- ` 开头**，一条一个点，能带具体数值就带。
3. **最后一行必须有 `验证：`**。

## 5. 两个完整样例

### 样例一：修一个会晃动的按钮

```
fix(ui): 配置名固定宽度不再顶动按钮，名字限制 20 个字

两个问题一起处理：

1. 切配置时「添加模组」会左右晃一下——工具栏那个按钮里的名字区是 MaxWidth，
   名字长短一变宽度就变，右边一栏又是右对齐，整个按钮跟着移动。改成固定
   Width=96 + 省略号，鼠标悬停看全名。标题行那串「配置「名字」· N 个模组」
   也补了 MaxWidth=520 + 省略号，免得 20 字的名字顶到右边的按钮上。

2. 名字上限 20 个字，按「字」算不按字符算：新增 Core/TextLimit，用
   StringInfo.ParseCombiningCharacters 数文本元素——一个汉字、一个字母都算 1，
   emoji（代理对）和带组合符的 é 也只算 1。直接按 string.Length 截会把代理对
   劈成半个字符。

   截断点在 ModLibrary.CreateProfile / RenameProfile（唯一真相），载入时
   Normalize 也把超长的旧名字收一遍。UI 的 prompt 文案写明上限，真截断了在
   成功的 toast 后面补一句「名字超过 20 个字，已截断」；查重放在截断之后，
   否则「超长名」和「截断后同名」会各判一次。

验证：.tmp/nameprobe/probe 27 项断言全 PASS（emoji 与组合字符都算 1 个字、
截断不劈代理对、配置新建/重命名都受同一套限制、空名字被拒）。
```

**这段在干什么**：标题说结果（不晃了 + 名字限长）。正文先说现象（切配置时按钮晃），再说根因（MaxWidth + 右对齐），再说修法（固定宽度 + 省略号）。第二件事连「为什么不按 string.Length」都交代了，因为那是踩过的坑。验证行具体到 27 项断言和 4 个检查点。

### 样例二：改一个时序问题

```
fix(ui): 忙等遮罩延迟 0.5 秒显示，别再闪一下

切配置时 DeployAsync 会拉起全屏遮罩，同步通常几十毫秒就完了，结果遮罩闪一下
就没了，比不显示还难受。

改成延迟显示：BeginBusy 只启动一个 500ms 的计时器，到点还没结束才把 IsBusy
置真；半秒内跑完的流程从头到尾不会出现遮罩。

另外补一个最短展示 200ms：0.5~0.7 秒的任务原本会出现遮罩闪 100 毫秒，
现在一旦显示就至少留 200 毫秒。EndBusy 若发现已展示够久就立刻收，
否则用另一个计时器延迟收；期间来了新任务会取消这个延迟，沿用同一个遮罩。

顺带处理：嵌套调用只在计数 0→1 时计时、1→0 时考虑收起；Dispose 里停掉两个计时器。

验证：.tmp/busyprobe/probe 在 STA 线程上真跑 DispatcherTimer，19 项断言全 PASS
（100ms 不显示、越 500ms 显示、可见时长 ≥200ms、嵌套不乱收、显示后来新任务不闪）。
```

**这段在干什么**：没有列表，因为改动是一条连续的时序链，拆成列表反而看不懂。验证行特别提到「在 STA 线程上真跑 DispatcherTimer」——因为 `DispatcherTimer` 在非 UI 线程上测不出真行为，这个细节说明验证是真的。

### 什么时候用列表，什么时候用段落

| 情况 | 写法 |
|---|---|
| 几个互不相干的改动 | 列表 |
| 一条连续的技术链 | 段落 |
| 两个独立问题一起修 | 编号 `1.` `2.` |

---

## 6. `验证：` 行的写法

| 有探针 | `验证：.tmp/xxxprobe/probe N 项断言全 PASS（括号里列检查点）` |
|---|---|
| 只有编译 | `验证：dotnet build 0 警告 0 错误` |
| 手工冒烟 | `验证：手工冒烟——启动、切 3 个配置、拖入 1 个 zip 导入成功` |
| 纯文档 | `验证：无（仅文档）` |

**不允许留空。** 没有验证的改动，等于没做完。

## 7. 分支与标签

| 项 | 现状 |
|---|---|
| 主分支 | `main`（唯一长期分支） |
| 工作分支 | 无固定命名，短期用 |
| 远程 | `origin` = fork，`upstream` = 上游 |
| 标签 | `vMAJOR.MINOR.PATCH`，与 csproj 的 `Version` 对齐 |

已有标签：`v2.0.0` / `v2.0.3` / `v2.0.5` / `v2.0.6`。

发版流程就是：改版本号 → 构建 → 提交 → 打 tag。
