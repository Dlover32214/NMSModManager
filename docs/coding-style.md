# 编码风格

这篇描述一个 C# 文件和一份 XAML 资源字典**实际长什么样**。不是理想规范，是现状记录——照着写就能融进现有代码。

---

## 1. 编译器设定

两个项目都靠 csproj 固定这些取值，不在文件里写 `#nullable` 之类的指令。

| 配置 | `AllModsSky.App` | `AllModsSky.Core` |
|---|---|---|
| `TargetFramework` | `net8.0-windows` | `net8.0-windows` |
| `ImplicitUsings` | `enable` | `enable` |
| `Nullable` | `enable` | `enable` |
| `LangVersion` | `latest` | `latest` |
| `Deterministic` | `true` | `true` |
| `UseWPF` | `true` | — |
| `GenerateDocumentationFile` | 默认（不生成） | `false` |

**为什么 Core 也是 `-windows`**：Core 不含任何 WPF 类型，但 `GameLocator` 要读注册表（`Microsoft.Win32`），所以不能降到 `net8.0`。

**将来迁 .NET 10**：`TargetFramework` 在两个 csproj 各写一份，迁移时两处一起改。完整清单见 [build-and-release.md](build-and-release.md) 第 10 节。

**没有的东西**：无 `.editorconfig`、无 `Directory.Build.props`、无 `global.json`、无任何分析器或 `TreatWarningsAsErrors`。风格全靠模仿现有代码，编译器的容忍度是默认值。

## 2. 命名空间与文件组织

### 命名空间 = 目录

48 个手写 `.cs` 文件，**全部**是 file-scoped namespace，无一处 block-scoped：

```csharp
namespace AllModsSky.Core.Infrastructure;
```

命名空间与所在目录严格对应：

| 目录 | 命名空间 |
|---|---|
| `src/AllModsSky.Core/Models/` | `AllModsSky.Core.Models` |
| `src/AllModsSky.Core/Infrastructure/` | `AllModsSky.Core.Infrastructure` |
| `src/AllModsSky.Core/Integrations/` | `AllModsSky.Core.Integrations` |
| `src/AllModsSky.Core/Services/` | `AllModsSky.Core.Services` |
| `src/AllModsSky.App/ViewModels/` | `AllModsSky.App.ViewModels` |
| `src/AllModsSky.App/Services/` | `AllModsSky.App.Services` |
| `src/AllModsSky.App/Views/` | `AllModsSky.App.Views` |
| `src/AllModsSky.App/Mvvm/` | `AllModsSky.App.Mvvm` |
| `src/AllModsSky.App/Converters/` | `AllModsSky.App.Converters` |
| `src/AllModsSky.App/Controls/` | `AllModsSky.App.Controls` |

`App.xaml.cs` 和 `MainWindow.xaml.cs` 在项目根，命名空间是 `AllModsSky.App`。

### 一个文件可以有多个类型

按职责聚合，不按类型拆文件。现状：

| 文件 | 类型数 | 内容 |
|---|---|---|
| `Core/Models/Models.cs` | 7 | `ModKind` / `ModRecord` / `AppSettings` / `ConfigEntry` / `ModProfile` / `LibraryState` / `GameInfo` |
| `App/Converters/Converters.cs` | 6 | 6 个 `IValueConverter` |
| `App/ViewModels/ToolsViewModel.cs` | 6 | 5 个行 ViewModel + `ToolsViewModel` |
| `Core/Infrastructure/Infrastructure.cs` | 5 | `AppPaths` / `JsonStore` / `FileOps` / `Humanize` / `AppLog` |
| `Core/Services/DeploymentService.cs` | 4 | `DeployReport` / `ExternalMod` / `ModPresence` / `DeploymentService` |
| `Core/Integrations/NexusClient.cs` | 5 | 3 个 record + `NexusClient` + `Http` |

规则是「同一职责族的小类型跟随主类型」，不是「顺手往文件尾追加一个不相关的东西」。

### 没有文件头注释

48 个文件全部以 `using` 或 `namespace` 开头。没有 `// Copyright`、没有 `// <auto-generated>`、没有块注释头。版权信息只存在于 `AllModsSky.App.csproj` 的 `<Copyright>`。

## 3. using 组织

**跨命名空间的 using 已经不再写在文件里。** 两个 csproj 用 `<Using>` 集中注入：

```xml
<!-- AllModsSky.Core.csproj -->
<ItemGroup>
  <Using Include="AllModsSky.Core.Models" />
  <Using Include="AllModsSky.Core.Infrastructure" />
  <Using Include="AllModsSky.Core.Integrations" />
</ItemGroup>
```

```xml
<!-- AllModsSky.App.csproj -->
<ItemGroup>
  <Using Include="System.IO" />
  <Using Include="System.Net.Http" />
  <Using Include="AllModsSky.Core.Models" />
  <Using Include="AllModsSky.Core.Infrastructure" />
  <Using Include="AllModsSky.Core.Services" />
  <Using Include="AllModsSky.Core.Integrations" />
</ItemGroup>
```

### 两条硬规则

**Core 只注入 `AllModsSky.Core.*`，永远不加任何 `System.*`。** 普通 SDK 的隐式 using 已经含 7 条 `System.*`，重复添加会在生成文件里产生重复条目。

**Core 不注入 `AllModsSky.Core.Services`。** Services 是最上层，一旦全局注入，`Infrastructure/` 里的文件就能在文件头看不出任何依赖的情况下反向调用 `ModLibrary`，分层会被悄悄破坏。不注入等于用编译器给依赖方向上了一道锁。

### App 为什么要单独加 `System.IO` 和 `System.Net.Http`

WPF SDK 的隐式 using 只有 5 条（`System` / `System.Collections.Generic` / `System.Linq` / `System.Threading` / `System.Threading.Tasks`），比普通 SDK 少 `System.IO` 和 `System.Net.Http`。这两条必须显式加，否则 `File`、`Path`、`HttpClient` 全线 CS0246。

### 文件里还留什么 using

只留 `ImplicitUsings` 覆盖不到的**同项目内其它命名空间**，比如：

```csharp
// App.xaml.cs
using System.Security.Cryptography;
using System.Text;
using System.Windows;
using System.Windows.Threading;
using AllModsSky.App.Services;
using AllModsSky.App.ViewModels;
```

顺序是 `System.*` → `Microsoft.*` → `AllModsSky.App.*`，各自按字母序。

### 全局 using 的代价

注入之后，**从文件头看不出跨目录依赖**。判断某个文件依赖哪些层，要看 csproj 的 `<Using>` 清单加目录图，不要看 `using` 列表。

另一个副作用：两个子命名空间出现同名类型会在使用点报 CS0104 歧义。Core 目前 64 个类型无重名。**新增类型前先 grep 一下简单名**。

## 4. 类型声明

### 默认 `sealed`

全项目 73 处 `sealed` 声明。没 sealed 的只有 10 个 XAML partial 类（`App` / `MainWindow` / `DialogWindow` / `ModPickerWindow` / 6 个 `*View`）和抽象基类 `ObservableObject`。

### `record` 只用于不可变 DTO

```csharp
// Core/Integrations/NexusClient.cs
public sealed record NexusFile(string Name, string Version, string? Url);

// Core/Infrastructure/VersionParser.cs
public sealed record ParsedVersion(double Value, bool IsMinimum, string Raw);

// Core/Infrastructure/PathGuard.cs
public readonly record struct Entry(string Path, bool IsDirectory);
```

需要 JSON 往返、需要可变的对象一律用可写属性 class，比如 `ModRecord` / `AppSettings` / `ModProfile`。

### 不用的特性

| 特性 | 现状 |
|---|---|
| `required` | 0 处 |
| 主构造函数（class） | 0 处，只有 record 用位置参数 |
| `ConfigureAwait` | 0 处——WPF 需要回到 UI 线程，加了反而要手动切回来 |
| `#nullable` 指令 | 0 处，只靠项目级开关 |
| `TODO` / `FIXME` / `HACK` | 0 处 |

### `async void` 只允许两种场景

| 位置 | 理由 |
|---|---|
| `ICommand.Execute` | 接口签名就是 `void` |
| WPF 事件处理器 | 事件签名就是 `void` |

`Mvvm/RelayCommand.cs` 的 `AsyncRelayCommand.Execute` 是第一种，内部自带重入保护和异常兜底：

```csharp
public async void Execute(object? parameter)
{
    if (!CanExecute(parameter)) return;
    _running = true;
    RaiseCanExecuteChanged();
    try { await _execute(parameter); }
    catch (Exception ex) { AppLog.Error(ex, "命令执行失败"); }
    finally { _running = false; RaiseCanExecuteChanged(); }
}
```

`MainWindow.xaml.cs` 的 `Window_PreviewDrop` / `Window_Drop` 是第二种。

除这两类之外的 `async void` 都是待改项，见 [deviations.md](deviations.md)。

### 不用 `.Result` / `.Wait()`

全项目只有 `Core/Services/Importer.cs` 一处 `.Result`（在 async 方法里阻塞等进程输出），属已知例外。

## 5. 成员与表达式

| 习惯 | 示例 |
|---|---|
| `var` 极重度使用 | 754 行以 `var` 开头 |
| 表达式体成员 | `protected void Raise(...) => PropertyChanged?.Invoke(...)` |
| 单行 `if` 不加大括号 | `if (string.IsNullOrWhiteSpace(name)) return false;` |
| Allman 大括号 | 左括号换行 |
| 模式匹配 | `switch` 表达式、`is` 属性模式、`is not null` |

```csharp
// Core/Infrastructure/PathGuard.cs
public static bool IsSafeSegment(string? name)
{
    if (string.IsNullOrWhiteSpace(name)) return false;
    if (name is "." or "..") return false;
    return name.IndexOfAny(Path.GetInvalidFileNameChars()) < 0;
}
```

## 6. 命名

| 类别 | 规则 | 示例 |
|---|---|---|
| 类型 / 方法 / 属性 | PascalCase | `ModLibrary`、`FindExisting`、`IsValid` |
| 私有实例字段 | `_camelCase` | `_shell`、`_instanceMutex`、`_running` |
| 私有 `static readonly` | **PascalCase** | `Gate`、`MaxBytes`、`KeepArchives`、`BusyShowDelay` |
| 常量 | PascalCase | `ModProfile.NoneId` |
| 接口 | `I` 前缀 | `IShellUi`、`IActivatable` |
| 异步方法 | `Async` 后缀 | `InitializeAsync`、`RefreshAllAsync` |
| 命令属性 | `XxxCommand` | `ImportFilesCommand`、`AddModsCommand` |

**私有 `static readonly` 用 PascalCase 是本项目特色**，和 .NET 官方惯例（`_camelCase` 或 `s_camelCase`）不同。照现有代码写：

```csharp
// Core/Infrastructure/Infrastructure.cs
private static readonly object Gate = new();
private const long MaxBytes = 2L * 1024 * 1024;
private const int KeepArchives = 5;
```

## 7. 注释

### 全中文，零英文

364 行中文注释，0 行纯英文注释。

### 写「为什么」，不写「是什么」

这是最有价值的一条。反面例子是 `// 设置 IsBusy`，正面例子是：

```csharp
// Core/Infrastructure/PathGuard.cs
/// <summary>
/// 不信任 library.json 里的目录名。
/// 定位已有条目一律从磁盘枚举，索引里的字符串只用来「查找」，不用来拼路径；
/// 只有「新建目标」这一种场景才允许 Path.Combine，且名字必须通过 IsSafeSegment。
/// </summary>
```

```csharp
// Core/Services/AmumssService.cs
/// 版本号会拼进 cmd 命令行，必须白名单化：设置页里手填的 "5.60 & calc" 原本可以直接执行任意命令。
```

```csharp
// App/App.xaml.cs
// 双开会让两个实例同时改写 library.json 和 MODS 目录，先挡住。
// 注意：string.GetHashCode() 在 .NET Core 每进程随机化，必须用稳定哈希。
```

### XML doc 密度不均

`///` 共 552 行，占 11731 行的 4.7%。分布：

| 文件 | `///` 行 / 总行 |
|---|---|
| `Core/Infrastructure/PathGuard.cs` | 25 / 98（26%） |
| `App/Views/DragGeometry.cs` | 21 / 65（32%） |
| `Core/Models/Models.cs` | 39 / 225（17%） |
| `App/ViewModels/LibraryViewModel.cs` | 25 / 811（3%） |

规律是：**Core 里的公开 API 和不变量写得多，ViewModel 的属性基本不写**。`GenerateDocumentationFile=false`，所以 `<see cref>` 写了也不产出 XML，只当交叉指路用。

## 8. XAML 与资源

### 资源字典三分

| 文件 | 行数 | 只放什么 |
|---|---|---|
| `Themes/Dark.xaml` | 63 | `Color` + `SolidColorBrush` + 渐变，**零 Style** |
| `Themes/Light.xaml` | 63 | 与 Dark 的 `x:Key` 集合完全一致 |
| `Themes/Styles.xaml` | 631 | **只有 Style，零颜色字面量** |

`App.xaml` 合并 Dark + Styles，再注册 6 个 Converter（`BoolToVisibility` / `InverseBool` / `StringEquals` / `EnumEquals` / `NullToVisibility` / `CountToVisibility`）。

### 颜色成对命名

每组颜色有两个键：`XxxColor`（`Color`）+ `Xxx`（`SolidColorBrush`）。

```xml
<Color x:Key="BgColor">#FF0A0E13</Color>
<SolidColorBrush x:Key="Bg" Color="{StaticResource BgColor}" />
```

共 21 组语义色：`Bg` / `BgElev` / `Surface` / `Surface2` / `Surface3` / `Border` / `BorderSoft` / `Text` / `TextMuted` / `TextFaint` / `Accent` / `AccentHover` / `AccentSoft` / `AccentText` / `Ok` / `OkSoft` / `Warn` / `WarnSoft` / `Danger` / `DangerSoft` / `Selection`。

### 主题刷子只能用 `DynamicResource`

`ThemeManager` 在运行时整个替换字典，用 `StaticResource` 引用主题刷子会切不动主题。

现状：`DynamicResource` 203 次，用 `StaticResource` 引用主题刷子的地方 **0 处**。`StaticResource` 的 426 次全部用于 Style 和 Converter 引用——这些不随主题变。

```xml
<!-- 对 -->
<TextBlock Foreground="{DynamicResource TextFaint}" />
<!-- 错 -->
<TextBlock Foreground="{StaticResource Text}" />
```

### 样式命名

语义名与形态名混用，分节注释隔开：

```xml
<!-- ===================== 文本 ===================== -->
<Style x:Key="H1" TargetType="TextBlock"> ...
```

语义名：`H1` / `H2` / `H3` / `Card` / `CardSoft` / `Divider` / `MutedText`
形态名：`Glyph` / `MonoText` / `ButtonBase`

### DataTemplate

页面级 6 个集中在 `MainWindow.xaml`，靠 `DataType` 映射到 View：

```xml
<DataTemplate DataType="{x:Type vm:LibraryViewModel}">
    <views:LibraryView />
</DataTemplate>
```

条目级两种写法都有：带 `DataType` 的（`LibraryView.xaml`、`ModPoolView.xaml`）和不带 `DataType` 的匿名模板（`DiscoverView.xaml`、`ModPickerWindow.xaml`）。

### 字体

**没有字体资源键。** `FontFamily="Segoe UI, Microsoft YaHei UI"` 在 `MainWindow.xaml`、`DialogWindow.xaml`、`ModPickerWindow.xaml` 各硬编码一次。

### 硬编码颜色

46 处，其中 29 处在 `MainWindow.xaml`（品牌 logo 的 `#5538BDF8`、`#0038BDF8` 这类渐变）。规律是**品牌装饰允许局部硬编码，业务 UI 一律走资源键**。
